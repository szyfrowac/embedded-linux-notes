## strace: what the program asks the kernel

Most "it just doesn't work" bugs on a target are a missing file, a wrong permission or a device that does not answer. `strace` shows every system call and its result:

```bash
strace -f -e trace=openat,connect ./myapp
```

A typical finding looks like this (illustrative):

```text
openat(AT_FDCWD, "/etc/myapp.conf", O_RDONLY) = -1 ENOENT (No such file or directory)
```

`-f` follows child processes and threads. Without `-e`, strace prints everything, which is useful once and overwhelming afterwards.

For timing, summarise instead of listing:

```bash
strace -c -f ./myapp
```

The table at the end shows each syscall's count and total time. A program that spends most of its time in `read` with thousands of calls is often reading one byte at a time.

## ltrace: library calls

`ltrace` does the same for calls into shared libraries:

```bash
ltrace -e malloc+free ./myapp
```

It is slower than strace and depends on the binary's dynamic linking, so it does not see inside statically linked programs.

:::caution[Tracing changes timing]
strace and ltrace stop the program at every traced call. A race condition can disappear under tracing, and a real-time loop will miss its deadlines. Use them to find logic errors, not to measure latency.
:::

## perf: where the CPU time goes

`perf` samples the program counter many times a second and reports which functions were running:

```bash
perf record -g ./myapp
perf report --stdio | head -40
```

`-g` records call graphs so you see who called the hot function. For a running service, attach by PID: `perf record -g -p <pid> -- sleep 10`.

For readable function names, perf needs symbols: build with `-g` and keep the binary unstripped, or point perf at the debug tree with `--symfs`. Some kernels need `CONFIG_PERF_EVENTS` enabled, and on boards without a hardware performance counter driver perf falls back to software timer sampling, which is coarser but still useful.

`perf top` gives a live view, like `top` but for functions.
